# Il bootstrap si revisiona come sistema, su due livelli

La lettura comparata dei sei adottanti (`i2/bootstrap-adottanti.md`) ratifica
la generalizzazione nata dalla riscrittura di `salute`: nel README il dominio
ha priorità editoriale sulla mappa strutturale e l'inventario completo deve
restare verificabile senza essere incorporato nella bussola. Non ratifica però
una revisione isolata del README né un template uniforme.

Il bootstrap è il quartetto coordinato `README.md` / `CLAUDE.md` / `goal.md` /
`world.md`. Il verdetto è a **due livelli**:

- `metodo` custodisce il contratto comune, confronta i repo e pubblica una
  prescrizione con criteri e tensioni osservate;
- ogni adottante verifica quei criteri contro il proprio dominio e applica o
  motiva le differenze mediante la propria skill `/method`.

La fotografia per repo non vive nel nodo canonico `kb/readme.md`, perché
diventerebbe rapidamente una seconda fonte stale. Vive nella sintesi i2 e
nell'audit periodico; i nodi canonici conservano soltanto gli invarianti emersi.

La prescrizione `o3/revisione-bootstrap-adottante.md` è aperta. Il filo si
chiude quando i sei adottanti hanno registrato nel proprio marker `/method` un
esito sulla revisione coordinata, incluse le divergenze motivate; non richiede
che i file abbiano uguale ordine o lunghezza.

La revisione è nata da una modifica diretta autorizzata dal custode attraverso
un repo che mantiene personalmente. Non è un errore di canale: nei repo sotto
la stessa ownership l'agente incaricato può modificare il canone, che passa poi
dal normale gate di review e commit di `metodo`. Per adottanti mantenuti da
terzi, invece, il confine è una pull request: il suo diff e il suo razionale
sono il segnale persistente che entra nella valutazione del canone.
